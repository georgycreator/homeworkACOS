# IDZ3 — процессная модель дуэли двух государств

Индивидуальное задание №3 по дисциплине «Архитектура компьютера и операционные системы».

**Вариант:** 7 — «Два условных государства»<br>
**Исполнитель:** Андрюшко Георгий Павлович<br>
**Группа:** БПИ253<br>
**Год:** 2026<br>
**Язык:** C11 / POSIX<br>
**Платформа:** Linux<br>

Проект развивает игровую модель IDZ2. Предметная логика сохранена: цели разных типов и стоимости, случайная/центральная/секторная стратегия, точность выстрела, обычные и тяжёлые снаряды, площадь поражения, боезапас, пополнение, стоимость боеприпасов, экономический лимит, статистика и причины прекращения огня. Переписан исполнительный слой: вместо `pthread_create()` используются отдельные процессы, POSIX Shared Memory и POSIX-семафоры.

## 1. Что реализовано для IDZ3

| Требуемый уровень | Исполняемая реализация | IPC |
|---|---|---|
| 4–5 баллов | `IDZ3` / `IDZ3_named` — один родитель создаёт четыре дочерних процесса через `fork()` | POSIX Shared Memory + именованные POSIX-семафоры (`sem_open`) |
| 6 баллов | `IDZ3_unnamed` — та же процессная модель | POSIX Shared Memory + неименованные POSIX-семафоры (`sem_init(..., pshared=1, ...)`) |
| 7–8 баллов | `IDZ3_init`, `IDZ3_coordinator`, `IDZ3_side`, `IDZ3_artillery` запускаются отдельно | POSIX Shared Memory + именованные POSIX-семафоры |

Во всех режимах работают пять участников модели:

1. координатор;
2. государство A;
3. государство B;
4. артиллерия A;
5. артиллерия B.

Два процесса-государства выполняют пополнение боезапаса и проверяют собственные условия прекращения огня. Два процесса артиллерии независимо выбирают координаты и обстреливают только территорию противника. Координатор начинает такты, отслеживает завершение, обрабатывает SIGINT/SIGTERM и собирает итоговую статистику.

## 2. Сборка

Зависимости:

```bash
sudo apt update
sudo apt install build-essential cmake ninja-build
```

Сборка всех вариантов:

```bash
cmake -S . -B build -G Ninja
cmake --build build -j4
```

Будут созданы:

```text
build/IDZ3                 # именованные семафоры, родитель + дети
build/IDZ3_named           # то же, явное имя варианта
build/IDZ3_unnamed         # неименованные семафоры в общей памяти
build/IDZ3_init            # создание конфигурации независимой сессии
build/IDZ3_coordinator     # отдельный координатор
build/IDZ3_side            # процесс государства A или B
build/IDZ3_artillery       # процесс артиллерии A или B
build/IDZ3_cleanup         # удаление зависшей независимой сессии (если потребуется)
```

## 3. Запуск реализаций для 4–6 баллов

Именованные POSIX-семафоры:

```bash
./build/IDZ3 scripts/cases/case1.conf
# или
./build/IDZ3_named scripts/cases/case1.conf
```

Неименованные POSIX-семафоры в разделяемой памяти:

```bash
./build/IDZ3_unnamed scripts/cases/case1.conf
```

Интерактивная настройка поддерживается обоими родительскими вариантами:

```bash
./build/IDZ3 --interactive
./build/IDZ3_unnamed --interactive
```

Справка:

```bash
./build/IDZ3 --help
```

Родительский процесс открывает лог, создаёт Shared Memory, инициализирует семафоры и запускает четыре дочерних процесса через `fork()`. По окончании он выставляет флаг остановки, будит процессы семафорами, дожидается каждого через `waitpid()`, копирует итоговое состояние обратно в основной конфигурационный объект и удаляет IPC-ресурсы.

## 4. Запуск независимых процессов для 7–8 баллов

### Автоматический запуск отдельных программ

```bash
./scripts/run_independent.sh demo42 scripts/cases/case1.conf
```

Скрипт вызывает отдельные исполняемые файлы и не заменяет их на потоки или `fork()`-потомков друг друга.

### Ручной запуск из разных терминалов

Сначала собрать конфигурацию и общую область памяти:

```bash
./build/IDZ3_init session42 scripts/cases/case1.conf
```

Затем запустить координатор (он откроет лог и будет ждать регистрации участников):

```bash
./build/IDZ3_coordinator session42
```

В четырёх других терминалах запустить участников:

```bash
./build/IDZ3_side session42 A
./build/IDZ3_side session42 B
./build/IDZ3_artillery session42 A
./build/IDZ3_artillery session42 B
```

Координатор начинает моделирование только после регистрации четырёх уникальных ролей: `side-A`, `side-B`, `artillery-A`, `artillery-B`. Повторная регистрация роли или PID переводит сессию в аварийную остановку. Во время моделирования координатор контролирует PID участников и обнаруживает преждевременное завершение процесса. В лог записываются PID, роль, события выстрелов, результаты попаданий, карты и итоговая статистика.

Если сессия была инициализирована, но запуск участников прервался до координатора, удалить ресурсы можно командой:

```bash
./build/IDZ3_cleanup session42
```

После штатного завершения координатор самостоятельно закрывает и удаляет именованные семафоры и POSIX Shared Memory.

## 5. Модель общей памяти и синхронизация

Одна POSIX-область Shared Memory содержит заголовок сессии, параметры конфигурации, состояния двух сторон, статистику, состояния тактов, PID участников и два массива клеток. Для динамических массивов в заголовке хранятся смещения от начала отображения, а не абсолютные адреса указателей. Поэтому независимо запускаемые процессы могут отображать объект по разным адресам и при этом корректно адресовать одни и те же клетки.

В общей части `config_t` указатели `grid.cells` не используются как межпроцессные адреса: они обнуляются при сохранении. Каждый участник создаёт локальное представление конфигурации и восстанавливает указатели на клетки относительно своего адреса `mmap()`. Массивы клеток при этом остаются общими и изменяются непосредственно в Shared Memory.

Состояние защищается robust process-shared `pthread_mutex_t` с атрибутами `PTHREAD_PROCESS_SHARED` и `PTHREAD_MUTEX_ROBUST`. Это не создаёт потоки: мьютекс используется только как межпроцессная блокировка критической секции. Она делает атомарными проверку завершения, расход боеприпаса, выстрел, изменение клетки, статистику и запись соответствующих сообщений в лог. Если владелец погибает внутри критической секции, `EOWNERDEAD` переводит модель в fail-stop: программа не продолжает игру с потенциально частично изменённым состоянием, а завершает её с ошибкой.

Семафоры используются для синхронизации действий участников:

- `side_tick_A/B` — координатор сообщает процессам государств о начале такта;
- `side_ack_A/B` — государства подтверждают обслуживание такта;
- `fire_tick_A/B` и `fire_ack_A/B` — в быстром режиме координатор разрешает выстрел и получает подтверждение;
- `ready` — регистрация рабочих процессов.

В варианте с неименованными семафорами объекты `sem_t` размещаются в общей памяти и инициализируются с `pshared=1`. В остальных вариантах каждый процесс открывает именованные семафоры по имени сессии.

### Режимы времени

- `tick_ms > 0`: государства обрабатывают новый такт по сигналу семафора; артиллерия работает независимо и проверяет готовность к выстрелу с коротким интервалом опроса. Задержка реакции и случайный разброс сохраняются. Если подразделение не готово к моменту смены такта, оно может пропустить этот такт — как и в исходной модели IDZ2.
- `tick_ms = 0`: координатор выполняет рукопожатие с обоими процессами артиллерии. Каждое подразделение делает не более одного выстрела (обычного или тяжёлого) за такт, если может стрелять. Задержка реакции не применяется.
- При `tick_ms > 0` ограничение `max_ticks` проверяется только после полного временного интервала последнего такта, поэтому `max_ticks=1` не отменяет выстрелы первого такта.

## 6. Сохранённая игровая логика

Сохранены исходные модули:

- `artillery.c` — xorshift32, независимый seed, стратегии `random`, `center`, `sector`, точность и проверки экономической доступности;
- `side.c` — обычный выстрел, тяжёлый площадной залп, пополнение, прекращение огня;
- `grid.c` — клетки `EMPTY`, `TARGET`, `DESTROYED`, типы целей, стоимость и агрегаты;
- `config.c` — значения по умолчанию, конфигурационный файл и интерактивный ввод;
- `io.c`, `log.c`, `colors.c`, `signals.c` — POSIX I/O, логирование, цветной интерфейс и сигналы.

Изменение предметной логики не было целью миграции. Основные правки сосредоточены в `ipc.c` и `process_simulation.c`, а идентификатор огневого участника в сообщениях заменён с `pthread` на PID.

## 7. Завершение и очистка

В родительских режимах координатор устанавливает `stopping`, разблокирует ожидающие процессы семафорами и вызывает `waitpid()` для всех созданных PID. В независимом режиме координатор выставляет общий флаг остановки, посылает семафорные уведомления, ожидает завершения рабочих процессов и удаляет объекты IPC.

SIGINT и SIGTERM обрабатывает координатор. В дочерних/рабочих процессах эти сигналы игнорируются, чтобы они не завершались независимо от координатора: остановка распространяется через общую память и семафоры. Это позволяет выполнить общий протокол очистки.

## 8. Тестирование

Запуск набора проверок:

```bash
./scripts/run_tests.sh
```

Набор содержит 36 интеграционных проверок: базовые игровые сценарии, тяжёлые удары, бюджет, повторные попадания, пополнение, минимальные карты, быстрый и замедленный режимы, полный последний такт при `max_ticks=1`, SIGINT для обоих родительских вариантов и независимой модели с проверкой очистки IPC, отказ на некорректной конфигурации, обработку ошибки `read()`, нормальный независимый запуск, запрет повторной регистрации одной роли, обнаружение `SIGKILL` независимого и дочернего рабочего процесса и fail-stop при `EOWNERDEAD`. В конце проверяется отсутствие оставшихся именованных семафоров и объектов Shared Memory.

Тесты не подменяют полную проверку по требованиям преподавателя: для демонстрации независимого режима рекомендуется дополнительно показать `ps -o pid,ppid,stat,comm` во время работы и отдельные терминалы для пяти программ.
