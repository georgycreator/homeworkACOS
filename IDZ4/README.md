# IDZ4 — «Мортирная дуэль» по TCP (клиент-серверная версия IDZ3)

Два условных государства на прямоугольных клеточных территориях асинхронно обстреливают друг друга
из миномётов. Цели, боезапас, бюджет, точность, стратегия, пополнение запасов и условия прекращения
огня — как в IDZ3. Отличие: вместо процессов с разделяемой памятью система теперь состоит из
**независимых сетевых программ**, общающихся по **TCP**, поэтому её участников можно разнести по
разным компьютерам.

Язык — C (libc, POSIX-системные вызовы, сокеты BSD). Платформа — Linux. Внешних библиотек нет.

---

## 1. Сборка

```bash
make                  # обычная сборка → build/idz4_{server,side,artillery,observer}
# или
cmake -S . -B build && cmake --build build
```

Для проверки памяти (ASan + UBSan):

```bash
make BUILD=build-asan EXTRA_CFLAGS="-fsanitize=address,undefined -fno-omit-frame-pointer -O1" \
     LDFLAGS="-fsanitize=address,undefined"
IDZ4_BIN=$PWD/build-asan ./scripts/run_tests.sh
```

## 2. Быстрый старт

Одна команда — вся система на localhost (наблюдатель печатает на экран, остальные — в `logs/`):

```bash
./scripts/run_local.sh                                  # сценарий case1, порт 5000
./scripts/run_local.sh scripts/cases/net_long.conf 6000 # другой сценарий и порт
```

Вручную, в **шести терминалах** (порядок запуска любой — клиенты сами повторяют подключение):

```bash
# 1. Сервер-координатор (читает конфигурацию, ждёт четырёх участников)
./build/idz4_server --listen 0.0.0.0 --port 5000 scripts/cases/case1.conf
# 2-3. Государства
./build/idz4_side      -s 127.0.0.1 -p 5000 -r A
./build/idz4_side      -s 127.0.0.1 -p 5000 -r B
# 4-5. Огневые подразделения
./build/idz4_artillery -s 127.0.0.1 -p 5000 -r A
./build/idz4_artillery -s 127.0.0.1 -p 5000 -r B
# 6. Наблюдатель (можно запускать сколько угодно, когда угодно)
./build/idz4_observer  -s 127.0.0.1 -p 5000
```

**На нескольких компьютерах**: сервер запускается на машине с адресом, например, `192.168.1.10`
(`--listen 0.0.0.0` или конкретный адрес), а во всех клиентах указывается `-s 192.168.1.10 -p 5000`.
Нужно лишь, чтобы TCP-порт сервера был доступен (фаервол). Конфигурационный файл нужен
**только серверу**: клиенты получают всё необходимое по сети.

### Ключи командной строки

| Программа | Ключи |
|---|---|
| `idz4_server` | `-l/--listen IP` (0.0.0.0) · `-p/--port N` (5000; `0` — свободный) · `--port-file FILE` · `-c/--config FILE` или позиционно · `-i/--interactive` (ввод параметров с клавиатуры) · `--log FILE` · `--grace SEC` (60) · `--reply-timeout MS` (5000) · `--history N` (1000) · `--min-observers N` · `--quiet` · `-h` |
| `idz4_side`, `idz4_artillery` | `-s/--server IP-или-имя` (127.0.0.1) · `-p/--port N` (5000) · **`-r/--side A\|B`** · `--retries N` (20) · `--retry-ms MS` (250) · `--log FILE` · `--quiet` |
| `idz4_observer` | то же, без `-r` |

Формат конфигурационного файла **не изменился** по сравнению с IDZ3: ключи `max_ticks`, `tick_ms`,
`seed`, `log`, а для каждой стороны `A.`/`B.` + `name rows cols ammo ammo_cost budget accuracy strategy
reaction_ms reaction_jitter_ms area_ammo area_cost area_radius area_every replenish_every
replenish_amount target`. Примеры — в `scripts/cases/`.

## 3. Сценарий: как сущности предметной области отображаются в программы

Условие требует, чтобы «обе стороны, их огневые подразделения и координатор моделирования» были
самостоятельными участниками. Поэтому каждая сущность — отдельная сетевая программа:

| Сущность модели | Программа | Что делает |
|---|---|---|
| Координатор моделирования | `idz4_server` | Владеет достоверным состоянием обеих территорий и боезапаса, ведёт такты, **регистрирует каждый выстрел**, проверяет инварианты, принимает подключения, рассылает события. |
| Государство A / B | `idz4_side -r A\|B` | Хранит **только свою** территорию и потери; сам инициирует пополнение запаса по своему расписанию; подтверждает каждый такт. О территории противника ничего не знает. |
| Огневое подразделение A / B | `idz4_artillery -r A\|B` | Само выбирает координаты по стратегии (random/center/sector), само «бросает кубик» точности, само выдерживает интервал между выстрелами. Знает только размеры поля противника. |
| Наблюдатель | `idz4_observer` | Показывает комплексную картину: журнал обеих сторон, карты территорий, итоги. Много наблюдателей (до ≈1000, см. §8), подключение и отключение в любой момент; поздно подключившийся получает последние `--history` строк журнала и текущее состояние. |

```
 idz4_artillery A ──SHOT──►┐                         ┌──RESULT──► idz4_artillery A
 idz4_artillery B ──SHOT──►│                         │──RESULT──► idz4_artillery B
 idz4_side A  ◄─TICK/IMPACT┤      idz4_server        ├──EVT────► idz4_observer #1..N
 idz4_side B  ◄─TICK/IMPACT┤   (poll, один процесс)  │
 idz4_side A/B ──ACK/RESUPPLY──►                     └──END────► все клиенты
```

Принцип безопасности инварианта «сторона меняет только территорию противника посредством
зарегистрированного выстрела»: клиент **не может** изменить ничего напрямую — он лишь присылает
запрос `SHOT`, а сервер проверяет и применяет его к территории противника.

### Такт модели

1. **Фаза государств.** Сервер шлёт `TICK n` государствам. Каждое при наступлении срока присылает
   `RESUPPLY n k` (пополнение каждые `replenish_every` тактов) и затем `ACK n`.
2. Сервер проверяет условия прекращения огня и шлёт подразделениям `GUNTICK n …` (остаток снарядов,
   доступность обычного/тяжёлого выстрела, «пора ли тяжёлым»).
3. **Фаза огня.** Подразделение присылает `SHOT n R|H строка столбец бросок` или `PASS n`.
   Сервер валидирует запрос, списывает **ровно один** снаряд, применяет попадание к территории
   противника, отвечает стрелку `RESULT`, пострадавшему государству — `DTGT`/`IMPACT`, наблюдателям — журнал и карты.
4. **Конец такта.**
   * `tick_ms = 0` — быстрый режим: такт закрывается, когда ответили оба подразделения. Порядок
     исполнения двух выстрелов одного такта **чередуется**: в чётных тактах первой стреляет A, в
     нечётных — B. Как и в IDZ3, выстрел, уничтоживший последние цели противника, сразу останавливает
     его огонь (его выстрел в этом такте не исполняется). Результат воспроизводим при том же `seed`,
     и ни одна сторона не имеет постоянного приоритета.
   * `tick_ms > 0` — по таймеру; подразделение, не уложившееся в такт (перезарядка, `reaction_ms`),
     пропускает его, а опоздавший `SHOT` отклоняется (`RESULT … late`).
5. Завершение: обе стороны прекратили огонь **или** достигнут `max_ticks` **или** Ctrl+C на сервере
   (если `max_ticks=0`). Условия прекращения стороны — как в IDZ3: все цели уничтожены / у противника
   не осталось целей / нет боеприпасов (с учётом пополнения) / исчерпан бюджет.

### Завершение и переподключения (описание поведения)

* **Штатный конец.** Сервер печатает итоги, шлёт каждому участнику `SUMMARY` и `END <причина>`,
  дожидается отправки и закрывает соединения. Все клиенты выходят с кодом `0`.
* **Ctrl+C на сервере** (`SIGINT`/`SIGTERM`) — то же самое с причиной «прерывание оператором»:
  **все клиенты завершаются корректно**, сервер выходит с кодом `0`.
* **Ctrl+C на клиенте** — клиент шлёт `BYE` и выходит с кодом `0`; для сервера это отключение участника.
* **Отключился участник** (упал, `kill -9`, обрыв сети): сервер **не падает**, а ставит бой на **паузу**
  на том же такте и ждёт возвращения (до `--grace` секунд, 60 по умолчанию). Достаточно заново запустить
  ту же команду клиента: он получает текущее состояние и **продолжает с того же места**. Подразделение
  в каждом `SHOT` присылает точное состояние своего ГПСЧ и позиции обхода секторов (после всех
  случайных чисел, потраченных на этот выстрел); сервер хранит их и отдаёт вернувшемуся
  подразделению. Бой с отключениями даёт **ту же** последовательность выстрелов, что и без них
  (тест T15). Сервер сообщает `ВОЗОБНОВЛЕНИЕ`. Если участник не вернулся — сервер завершает бой с причиной «участник не вернулся»
  и кодом `1`. Отключение **наблюдателей** паузы не вызывает.
* **Зависший клиент.** Сервер раз в `reply-timeout/4` (100…1000 мс) шлёт каждому клиенту `PING`; кто
  дольше `--reply-timeout` не прислал вообще ничего (процесс завис, сеть оборвалась без FIN),
  отключается и далее обрабатывается как отключившийся. Это работает в **любом** режиме, в том числе
  при `tick_ms > 0`, где сервер не ждёт ответа на такт. В режиме `tick_ms = 0` дополнительно действует
  ожидание `SHOT/PASS`.
* **Сервер убит без предупреждения** — клиенты замечают обрыв, печатают сообщение и выходят с кодом `2`
  (не зависают).
* **Роль уже занята** — второй клиент получает `ERR` и выходит с кодом `1`; идущий бой не затрагивается.
* **Мусор на входе** (неизвестная команда, обрывки, двоичные данные, слишком длинная строка, команда
  до `HELLO`) — сообщение отклоняется, нарушитель отключается, остальные не страдают.

Коды возврата: клиенты — `0` штатно, `1` ошибка параметров/отказ сервера, `2` сервер недоступен/оборвался;
сервер — `0` штатно/по сигналу, `1` ошибка запуска, внутренняя ошибка или не вернувшийся участник.

## 4. Протокол (текстовый, построчный, `\n`)

Клиент → сервер: `HELLO <роль>` · `ACK <такт>` · `RESUPPLY <такт> <кол-во>` ·
`SHOT <такт> <R|H> <стр> <стлб> <бросок 0..99> <rng> <сектор>` · `PASS <такт>` · `PONG` · `BYE`.

Сервер → клиент: `WELCOME`/`CFG`/`STATE`/`MAP`/`TGT`/`WELCOME_END` (описание сессии) ·
`START` · `TICK` · `GUNTICK` · `RESULT` · `DTGT` + `IMPACT` · `SUPPLY` · `CEASEFIRE` ·
`PING` · `PAUSE`/`RESUME` · `TXT` · `EVT` (журнал для наблюдателей) · `SUMMARY` · `END` · `ERR`.

Полный формат каждого сообщения описан в комментарии `include/proto.h`. Роли: `side-A side-B gun-A gun-B observer`.
Транспорт — неблокирующие сокеты, `poll()`, построчная буферизация (`conn_t` в `net.c`),
очередь отправки ограничена 16 МБ (медленный наблюдатель отключается, а не тормозит бой).

## 5. Тесты

```bash
./scripts/run_tests.sh                 # все 16 групп (~1,5 мин)
./scripts/run_tests.sh reconnect garbage    # выбранные
```

| № | Что проверяет |
|---|---|
| T1 `lockstep_cases` | 15 конфигураций в режиме `tick_ms=0`: **полная итоговая сводка** (выстрелы, попадания, промахи, уничтоженные цели, остатки и расход боезапаса, потери, вердикт, число тактов) совпадает с эталоном, снятым с исходного IDZ3 (`tests/golden/*.sums`); если сам IDZ3 даёт разные исходы, IDZ4 обязан совпасть с одним из них |
| T2 `invariants` | выстрелы = попадания + промахи, нет отрицательных значений, не более одного выстрела за такт |
| T3 `realtime_observer` | бой в реальном времени; наблюдатель видит всё, государство — только свою карту, подразделение — карт не видит |
| T4 `observers_dynamic` | наблюдатели подключаются/отключаются (`kill -9`, `SIGTERM`) во время боя; поздний получает заголовок, историю уже сделанных выстрелов и текущее состояние |
| T5 `reconnect` | `kill -9` подразделения и государства → пауза → возврат → бой доигран все 80 тактов |
| T6 `server_sigint` | остановка сервера: 5 клиентов выходят с кодом 0 |
| T7 `server_kill9` | сервер убит: клиенты не зависают, код 2 |
| T8 `duplicate_role` | занятая роль отклоняется, бой не нарушается |
| T9 `garbage` | мусор, двоичные данные, строка без `\n`, команды до `HELLO` — сервер жив |
| T10 `bad_shots` | неверный снаряд/координаты/бросок, тяжёлый залп раньше срока, дубль и «выстрел из будущего» отклонены, исполнен ровно один |
| T11 `absent_timeout` | участник не вернулся → `--grace` → сервер выходит с кодом 1 |
| T12 `hung_client` | `SIGSTOP` подразделения **в обоих режимах** (`tick_ms=0` и `tick_ms>0`) → отключение по `--reply-timeout` (PING) → замена → бой возобновлён |
| T13 `startup_order` | клиенты запущены раньше сервера; `--min-observers` удерживает старт |
| T14 `cli_errors` | неверные порт/конфигурация/роль/хост, занятый порт |
| T15 `resume_exact` | бой на 100 000+ тактов с тремя `kill -9` подразделений даёт **побитово ту же** последовательность выстрелов и итог, что и бой без отключений (для стратегий `center` и `sector`, точность < 100 %, тяжёлые залпы) |
| T16 `many_observers` | 100 наблюдателей одновременно |

Ручные команды для отдельных сценариев:

```bash
# Реконнект: убейте любую клиентскую программу (Ctrl+\ или kill -9 PID) и просто запустите её снова.
# Динамические наблюдатели: в отдельном терминале сколько угодно раз
./build/idz4_observer -s 127.0.0.1 -p 5000        # Ctrl+C — отключиться, запустить снова — подключиться
# Ждать наблюдателя перед стартом
./build/idz4_server --min-observers 2 -p 5000 scripts/cases/net_long.conf
# Воспроизводимый быстрый бой (одинаковый seed — одинаковый результат)
sed 's/^tick_ms=.*/tick_ms=0/' scripts/cases/case1.conf > /tmp/fast.conf && ./build/idz4_server /tmp/fast.conf
# Остановка бесконечного боя: Ctrl+C на сервере — клиенты завершатся сами
./build/idz4_server -p 5000 scripts/cases/net_lockstep_long.conf
```

## 6. Что изменено относительно IDZ3

IDZ3 — многопроцессная программа на одной машине: `fork`, разделяемая память (именованная и
анонимная), семафоры/мьютексы, потоки в логе, отдельные программы `init/side/artillery/coordinator/cleanup`.
IDZ4 — **новая архитектура и новая логика взаимодействия**; из IDZ3 перенесена только предметная
модель (территория, цели, боезапас, стратегии, условия прекращения).

### 6.1. Удалено (не нужно в сетевой модели)

| Что было в IDZ3 | Почему удалено |
|---|---|
| `main.c`, `process_simulation.c`, `src/independent/*` (5 программ), `init`/`cleanup` | процессная модель и ручное создание/удаление IPC-объектов |
| `ipc.c/.h`, разделяемая память POSIX (named/unnamed), семафоры, мьютексы | общего адресного пространства больше нет — состояние живёт на сервере, обмен идёт сообщениями |
| `fork`/`waitpid`, пул процессов | участники — самостоятельные программы, которые запускает оператор |
| `pthread` в `log.c` | программы однопоточные (`poll()`), блокировки не нужны |
| сборка двух вариантов (`IDZ3_named`/`IDZ3_unnamed`) | вместо них — 4 программы по ролям |

### 6.2. Перенесено с доработкой

| Файл | Изменения |
|---|---|
| `grid.c/h` | Без изменений логики. Добавлены `grid_render` / `grid_render_targets` / `grid_row_chars`: карта формируется в буфер, чтобы её можно было и напечатать, и отправить по сети. `grid_print` теперь обёртка над `grid_render`. |
| `artillery.c/h` | Логика (ГПСЧ, стратегии, проверки боезапаса/бюджета) без изменений. `artillery_print_stats` заменена на `artillery_render_stats` (вывод в буфер). |
| `config.c/h` | Формат и валидация без изменений; сервер — единственный, кто читает конфигурацию. |
| `side.c/h` | Оставлено только описание данных стороны и вывод статистики (`side_render_stats`). Боевые функции (`side_fire`, `side_area_strike`, `side_replenish`, `side_check_done`) вынесены в `battle.c` и больше не печатают сами. |
| `log.c/h` | Однопоточный; добавлены `log_file` (только файл), `log_set_console`, и **приёмник** `log_set_sink` — через него всё, что сервер печатает, автоматически уходит наблюдателям. |
| `signals.c`, `io.c`, `colors.c` | Без изменений (используются сервером и клиентами). |

| `Makefile`, `CMakeLists.txt`, `scripts/run_tests.sh`, `run_local.sh`, `cases/net_*.conf` | сборка, автотесты, запуск, сетевые сценарии |
| `tests/summary.sh`, `tests/make_golden.sh`, `tests/golden/*.sums` | извлечение итоговой сводки; построение эталона по бинарнику IDZ3; сами эталоны (все наблюдавшиеся исходы IDZ3) |
| `scripts/cases/net_det.conf`, `case_replenish_after_stop.conf` | длинный детерминированный бой для проверки точного возобновления; пополнение после прекращения огня |

### 6.4. Изменения в поведении

1. **Единственный «источник истины» — сервер.** В IDZ3 территории лежали в разделяемой памяти, и любой
   процесс мог их читать/менять. Теперь изменить территорию можно только через `SHOT`, прошедший проверку сервера
   (формат, фаза, такт, дубликат, остаток снарядов, бюджет, границы поля, **срок тяжёлого залпа**).
2. **Секретность целей.** Подразделение узнаёт лишь размеры поля противника и итог своих выстрелов;
   государство — только собственную карту. В IDZ3 все процессы имели доступ к общей памяти.
3. **Бросок точности** делается подразделением (его ГПСЧ) и передаётся в `SHOT`; сервер применяет порог
   `accuracy`. Как и в IDZ3, ГПСЧ расходуется только при `accuracy < 100`.
4. **Порядок выстрелов внутри такта (`tick_ms=0`).** В IDZ3 два процесса артиллерии боролись за общую
   блокировку, поэтому порядок определялся планировщиком ОС: **итог IDZ3 в ряде сценариев недетерминирован**
   (при 8 прогонах `case3_area`, `case_tiny`, `case_types` дали по два разных исхода). В IDZ4 порядок
   фиксирован и **чередуется по чётности такта** (чётный — первой A, нечётный — первой B), а выстрел,
   уничтоживший последние цели противника, как и в IDZ3 останавливает его огонь немедленно. Следствия:
   результат воспроизводим; ни одна сторона не имеет постоянного приоритета; каждый такт соответствует
   одной из возможных расстановок IDZ3. Однако на спорных тактах (когда один выстрел решает исход)
   результат определяется чётностью такта, а не «гонкой» — поэтому IDZ4 совпадает с **одним из**
   исходов IDZ3, а не со всеми. В режиме `tick_ms>0` выстрелы исполняются в порядке прихода.
5. **Пополнение запаса** инициирует государство (`RESUPPLY`) по своему расписанию; сервер проверяет
   такт, количество и повторность. Как и в IDZ3, оно продолжается и у стороны, прекратившей огонь,
   пока идёт бой (в первой версии IDZ4 это было иначе, что искажало итоговый остаток снарядов;
   исправлено, закреплено кейсом `case_replenish_after_stop`: A прекращает огонь по бюджету, но к
   концу боя у неё 13 снарядов, как и в IDZ3).
6. **Тяжёлые залпы:** расписание (`area_every`) ведёт и **проверяет сервер**: залп принимается, если
   пришёл срок либо обычными снарядами стрелять нельзя (правило IDZ3); иначе — отказ `not-due`.
   Подразделение получает флаг «пора» в `GUNTICK`.
7. **Режим `tick_ms > 0`:** выстрел, пришедший после конца такта, отклоняется (в IDZ3 процессы жили
   в общих часах). Интервалы между выстрелами (`reaction_ms` + разброс) подразделение выдерживает само.
8. **Переподключение.** Состояние ГПСЧ и обхода секторов подразделения сервер получает в каждом `SHOT` и
   возвращает вернувшемуся клиенту — это **точное** восстановление (в первой версии оно вычислялось по
   числу выстрелов и было приблизительным). Не восстанавливается лишь время перезарядки (`reaction_ms`):
   оно не влияет на последовательность выстрелов, только на момент следующего.
9. **«Живость» клиентов.** Периодический `PING`/`PONG`: клиент, молчащий дольше `--reply-timeout`,
   отключается в любом режиме (в первой версии это работало только при `tick_ms=0`).
10. **История для наблюдателей.** Поздно подключившийся наблюдатель получает заголовок журнала,
    **последние `--history` строк** (по умолчанию 1000), а не весь журнал с начала боя, и текущее
    состояние территорий. Полный журнал — в файле сервера.
11. **Новое:** лобби, пауза/возобновление, `--grace`, `--reply-timeout`, `--min-observers`,
    наблюдатели в количестве до ≈1000, корректное завершение всех клиентов при остановке сервера.
12. **Вывод.** Участники печатают только то, что им прислано (государство — свою карту и потери,
    подразделение — свои выстрелы и результат). Карты больше 60×150 не рисуются (ни у наблюдателей,
    ни у государства) — выводится сводка. Полная картина — у наблюдателей и в журнале сервера.
13. **Журналы:** у каждой программы свой `--log`; журнал сервера — полный, с картами.

### 6.5. Проверка эквивалентности

Эталон снят с исходного бинарника IDZ3 для 15 конфигураций (`scripts/cases/*.conf`, кроме
заведомо некорректной `bad_cost`, бесконечной `case2` и сетевых `net_*`): каждая запускалась в режиме
`tick_ms=0` по 8 раз (`tests/make_golden.sh`). Сохранены **все** различные исходы (`tests/golden/*.sums`).

* В 12 кейсах IDZ3 всегда даёт один и тот же исход, и IDZ4 совпадает с ним по **всем** показателям:
  выстрелы, попадания, промахи, уничтоженные цели, остатки обычных и тяжёлых снарядов, расход,
  потери, вердикт, число тактов (включая 30 000 тактов `case_overflow`).
* В 3 кейсах (`case3_area`, `case_tiny`, `case_types`) сам IDZ3 недетерминирован (по 2 исхода);
  IDZ4 даёт стабильный исход, совпадающий с одним из них.

Тест T1 сравнивает именно полную сводку, а не только число тактов. Побитовой эквивалентности
**всех** возможных прогонов IDZ3 утверждать нельзя — только то, что описано выше.

## 8. Известные ограничения

* Протокол без шифрования и аутентификации — рассчитан на учебную/доверенную сеть.
* В режиме `tick_ms > 0` на медленной сети короткий такт (десятки мс) может «не успеть» за задержкой —
  выстрел будет отклонён как опоздавший; для сетевых запусков берите `tick_ms` ≥ 100.
* **Число соединений ограничено** константой `MAX_CLIENTS = 1024` в `server.c` (4 роли + наблюдатели,
  то есть до 1020 наблюдателей) и лимитом файловых дескрипторов процесса (`ulimit -n`, часто 1024).
  Для требования «множество наблюдателей» этого достаточно (проверено на 100), но «неограниченным»
  число не является.
* Поздний наблюдатель получает не всю историю боя, а последние `--history` строк журнала.
* Карты больше 60×150 клеток не рисуются (выводится сводка), чтобы не засорять канал и не тормозить клиентов.
* Состояние боя хранится в памяти сервера: при падении самого сервера бой не восстанавливается.
* Время перезарядки (`reaction_ms`) подразделения после переподключения не восстанавливается.
