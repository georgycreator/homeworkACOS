## 1. Условие задачи

Два условных государства расположены на прямоугольных клеточных территориях. На территории каждой
стороны размещены цели различного типа и стоимости. Стороны независимо и асинхронно производят
миномётные выстрелы по координатам территории противника, не зная, где находятся его цели. Выбор
цели — случайный или по заданной стратегии. Попадание в неповреждённую цель уничтожает её и уменьшает
суммарную стоимость оставшихся объектов; повторное попадание в разрушенную или пустую клетку
результата не даёт. У каждой стороны есть запас снарядов (возможно пополнение), бюджет
(экономическое ограничение) и точность. Бой стороны прекращается, если уничтожены все её цели,
исчерпан запас снарядов либо израсходован бюджет.

**Входные параметры:** размеры территорий; число, расположение и стоимость целей; число и стоимость
снарядов; интервалы между выстрелами; точность и стратегия выбора координат; правила пополнения;
условия экономического прекращения огня.

**Отображаемые события:** выстрел, координаты цели, промах, попадание, уничтожение объекта, остаток
снарядов, стоимость потерь, текущее состояние обеих территорий.

**Инварианты:** выстрел расходует не более одного снаряда; цель уничтожается только один раз;
стоимость и число оставшихся объектов не отрицательны; сторона меняет территорию противника только
зарегистрированным выстрелом; событие завершения останавливает новые выстрелы стороны.

**Завершение:** оба прекратили огонь, либо лимит тактов, либо прерывание пользователем (если число
тактов не ограничено). Обе стороны, их огневые подразделения и координатор — самостоятельные участники.

## 2. Сценарий: отображение сущностей модели в программы

Каждый самостоятельный участник модели — отдельная консольная программа на C; они общаются только
через TCP-сокеты (протокол — `include/proto.h`), поэтому могут работать на разных компьютерах.

| Сущность | Программа | Ответственность |
|---|---|---|
| Координатор | `idz4_server` | достоверное состояние обеих территорий и боезапаса; такты; регистрация и проверка каждого выстрела; лобби; пауза и возобновление; рассылка событий; итоги |
| Государство A, B | `idz4_side -r A\|B` | собственная территория и потери; запрос пополнения запаса по собственному расписанию; подтверждение тактов |
| Огневое подразделение A, B | `idz4_artillery -r A\|B` | выбор координат (random / center / sector); бросок точности; выдерживание интервала между выстрелами |
| Наблюдатель | `idz4_observer` | комплексная картина: журнал обеих сторон, карты, итоги |

Процессы здесь не создаются сервером: каждый участник запускается оператором отдельно (в этом
принципиальное отличие от IDZ3, где координатор порождал процессы через `fork`). Сервер — один
процесс с одним потоком, мультиплексирующий все соединения через `poll()`.

**Такт модели.** (1) Сервер шлёт государствам `TICK`; те при наступлении срока присылают `RESUPPLY`,
затем `ACK`. (2) Сервер проверяет условия прекращения огня и шлёт подразделениям `GUNTICK`. (3)
Подразделение присылает `SHOT` или `PASS`; сервер проверяет выстрел, списывает ровно один снаряд,
изменяет только территорию противника, отвечает стрелку (`RESULT`), пострадавшему государству
(`IMPACT`, `DTGT`), наблюдателям (журнал и карты). (4) Такт закрывается, когда ответили оба
подразделения (`tick_ms = 0`) либо по таймеру (`tick_ms > 0`).

**Соблюдение инвариантов** обеспечивает сервер: цель переходит из состояния «цель» в «разрушена»
только в одной функции (`destroy_cell`), поэтому повторно не учитывается; счётчики уменьшаются
только при таком переходе, поэтому не уходят в минус; клиент не может изменить территорию иначе
как запросом `SHOT`, прошедшим `battle_validate`; после сообщения `CEASEFIRE` новые выстрелы стороны
отклоняются (`ceasefire`).

## 3. Пользовательский интерфейс

Все программы — консольные, вывод информативен и цветной (в журнал-файл цвета не пишутся).

* **Сервер** печатает подключения и лобби, заголовок каждого такта, выстрелы с исходом
  (промах/попадание/уничтожение), прекращение огня, паузы и возобновления, отклонённые запросы,
  итоговую статистику и вердикт. Карты в ходе боя сервер на консоль не выводит — они идут
  наблюдателям и в журнал.
* **Государство** показывает только свою территорию: список своих целей, карту, каждый такт (целей,
  стоимость, потери), прилёты по своей территории, потерянные цели, пополнение запаса.
* **Подразделение** показывает только свои выстрелы: такт, координаты, бросок точности, результат,
  остаток обычных и тяжёлых снарядов, расход.
* **Наблюдатель** показывает всё: оба журнала, карты обеих территорий после каждого поражения, итоги.

Фрагмент вывода подразделения A (сценарий `case1`, `tick_ms=0`):

```
[АРТИЛЛЕРИЯ Северная] Готова к бою: цель — территория Южная (5x5), стратегия random, уже сделано выстрелов: 0
[СЕРВЕР] [СТАРТ] Все участники подключены (наблюдателей: 1). Начинаем моделирование.
[АРТИЛЛЕРИЯ Северная] такт 0: выстрел по (0,3), бросок точности 3
[АРТИЛЛЕРИЯ Северная]   -> ПРОМАХ (пустая клетка). Осталось: обычных 9, тяжёлых 2; израсходовано 2
```

Фрагмент государства A:

```
[ГОСУДАРСТВО Северная] такт 2: целей 2 (стоимость 15), потери 0
[ГОСУДАРСТВО Северная] такт 2: по нашей территории выстрел в (1,2) — мимо
```

Фрагмент журнала сервера:

```
========== ТАКТ 1 ==========
[АРТИЛЛЕРИЯ Южная] [такт 1] Выстрел по (2,1). Осталось снарядов: 8, израсходовано: 4
  -> ПРОМАХ (точность 60%, бросок 96)
[АРТИЛЛЕРИЯ Северная] [такт 1] Выстрел по (3,1). Осталось снарядов: 8, израсходовано: 4
  -> ПРОМАХ (пустая клетка)
```

(на нечётном такте первой стреляет B, на чётном — A: порядок чередуется).

## 4. Запуск и завершение

Сборка: `make` (или `cmake -S . -B build && cmake --build build`). Полный перечень ключей — в `README.md`.

```bash
./build/idz4_server -l 0.0.0.0 -p 5000 scripts/cases/case1.conf      # сервер (конфигурация — только у него)
./build/idz4_side      -s 192.168.1.10 -p 5000 -r A                  # государство A (и -r B)
./build/idz4_artillery -s 192.168.1.10 -p 5000 -r A                  # подразделение A (и -r B)
./build/idz4_observer  -s 192.168.1.10 -p 5000                       # наблюдатель (любое число, когда угодно)
./scripts/run_local.sh                                               # всё на одной машине одной командой
```

IP-адреса и порты задаются только в командной строке. Порядок запуска любой: клиенты повторяют
подключение (`--retries`, `--retry-ms`).

| Ситуация | Поведение | Код возврата |
|---|---|---|
| Обе стороны прекратили огонь / лимит тактов | итоги, `END` всем, штатное закрытие | сервер 0, клиенты 0 |
| Ctrl+C на сервере | `END` с причиной «прерывание оператором», все клиенты завершаются | сервер 0, клиенты 0 |
| Ctrl+C на клиенте | `BYE`; для сервера — отключение участника (пауза) либо ничего (наблюдатель) | 0 |
| Участник пропал (`kill -9`, обрыв сети, зависание) | пауза; возобновление при повторном запуске клиента; по `--grace` — завершение | сервер 1 при невозврате |
| Сервер убит без предупреждения | клиенты замечают обрыв и выходят | клиенты 2 |
| Роль занята / неверные параметры | отказ с сообщением | клиент 1 |
| Некорректные сообщения в канале | отклонение, отключение нарушителя, сервер продолжает | — |

## 5. Что реализовано по уровням оценки

| Уровень | Реализация |
|---|---|
| 4–5 | независимые сервер и клиенты, IP и порты в командной строке, работа на одной и нескольких машинах, каждый показывает только свои данные, завершение описано (§4) |
| 6–7 | `idz4_observer` — отдельный клиент с комплексной картиной |
| 8 | много наблюдателей (до ≈1000, проверено на 100), подключение и отключение в любой момент без влияния на бой; поздний наблюдатель получает историю (последние `--history` строк) и текущее состояние |
| выше 8 | отключение и повторный запуск любых участников при работающем сервере (пауза/возобновление, точное восстановление состояния подразделения); при остановке сервера все клиенты завершаются корректно |
| дополнительно | комментарии в коде; ввод-вывод через дескрипторы (`socket/recv/send/poll/read/write/open`); тестовые наборы и скрипты; опции `--log`, `--history`, `--grace`, `--reply-timeout`, `--min-observers`, `--port 0 --port-file`; сборка sanitizer'ами |

Изменения относительно IDZ3 подробно описаны в `README.md`, §6.

## 6. Результаты работы

**Эквивалентность игровой логики IDZ3.** Для 15 конфигураций сняты эталонные итоговые сводки с
исходного бинарника IDZ3 (по 8 запусков на кейс), IDZ4 сравнивается с ними по выстрелам, попаданиям,
промахам, уничтоженным целям, остаткам и расходу боезапаса, потерям, вердикту и числу тактов.
В 12 кейсах исход IDZ3 единственный и IDZ4 совпал полностью; в 3 кейсах (`case3_area`, `case_tiny`,
`case_types`) сам IDZ3 даёт по два разных исхода из-за гонки процессов, IDZ4 даёт один стабильный
исход, совпадающий с одним из них.

**Автоматические тесты** (`./scripts/run_tests.sh`, 16 групп): сравнение с эталоном; инварианты;
бой в реальном времени с наблюдателем; динамические наблюдатели (в том числе поздний с историей);
отключение и возврат участников (`kill -9`); остановка сервера (`SIGINT`, `SIGKILL`); занятая роль;
мусор и двоичные данные в канале; некорректные и преждевременные выстрелы; невозвращение участника;
зависший клиент (`SIGSTOP`) в обоих режимах; порядок запуска; ошибки командной строки; точное
возобновление подразделений после трёх отключений (последовательность выстрелов побитово
совпадает с контрольным боем); 100 одновременных наблюдателей.
Итог последнего полного прогона: **85 проверок успешно, 0 провалено** (§8). Дополнительно сетевые тесты проходят на сборке с
`-fsanitize=address,undefined`.

## 8. Выводы

Предметная модель IDZ3 перенесена без изменения правил, а координация переведена с общей памяти на
TCP-сообщения: единственным владельцем состояния стал сервер, участники — независимые программы.
Добавлены динамические наблюдатели, переподключение участников с точным восстановлением состояния,
контроль «живости» и корректное завершение при остановке сервера. Поведение, отличающееся от IDZ3
(порядок выстрелов в такте, ограничения числа наблюдателей и истории), явно описано.
